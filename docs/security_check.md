|---|---|---|
| 1 | 코드·과거 커밋에 API 키가 박혀 있지 않은가 | ✅ 없음 |

## 1. 키 하드코딩 확인

```
git grep -nE "AIza|sk-|Bearer [A-Za-z0-9]" -- . ':!*.md'   →  0건 (현재 코드)
git log --all -p -S"AIza" ...                              →  일치 없음
git log --all -p -S"sk-" ...                                →  "autodesk-" 오탐만, 실제 키 없음
git log --all -p -S"Bearer " ...                            →  전부 f-string 변수(`Bearer {token}`), 리터럴 키 없음
```

현재 코드와 커밋 히스토리 전체 어디에도 실제 API 키 문자열이 없다.

## 2. 환경변수 · `.env`

`ai_review.py`·`dwg.py`·`main.py`·`stats.py` 모두 `os.environ.get(...)`로만 키를
읽는다(`GEMINI_API_KEY`, `GOOGLE_API_KEY`, `CLOUDFLARE_API_TOKEN`,
`CLOUDFLARE_ACCOUNT_ID`, `GROQ_API_KEY`, `MISTRAL_API_KEY`, `CLOUDCONVERT_API_KEY`).
코드에 기본값으로 박힌 키는 없다.

**흠을 하나 찾았다.** `.gitignore`에 `.env`가 없었다. 지금 저장소에 커밋된 `.env`
파일은 없지만(`git ls-files | grep .env` → 0건), 누군가 로컬에서 `.env`를 만들어
쓰다가 실수로 `git add`하면 그대로 커밋될 수 있는 구조였다. 오늘 `.gitignore`에
`.env`, `.env.*`를 추가해 막았다.

## 3. `aicache/` 개인정보

```
git ls-files aicache/   → 0개
find aicache -type f    → 0개
```

폴더가 비어 있어 지금은 새는 개인정보가 없다. 캐시가 쌓이기 시작하면(실제 도면으로
채점을 여러 번 돌리면) 이 점검을 다시 해야 한다 — 파일명은 도면 그림 해시라 안전해도
**AI 응답 JSON 안 지적 문구에 표제란 이름이 섞여 들어갈 수 있다.**

## 4. 업로드 삭제

`main.py`의 `_prune_uploads()`(32~54행)는 `JOB_TTL_SEC=3600`(1시간) ·
`JOB_KEEP=20`으로 오래됐거나 20개를 넘는 작업 폴더를 지운다. 로컬에서 가짜 작업
폴더의 수정 시각을 1시간 2분 전으로 만들고 함수를 직접 불러 확인했다.

```
old 남음: False   ← 1시간 지난 폴더, 지워짐
new 남음: True    ← 방금 만든 폴더, 안 지워짐
```

로직 자체는 맞게 짜여 있다. **다만 이 함수가 09-01까지는 크론이 아니라 `_run()`
(새 검사 요청) 안에서만 불렸다.** 즉 어떤 작업 폴더가 1시간을 넘겨도, 그 뒤로 아무도
검사를 새로 요청하지 않으면 다음 요청이 올 때까지 디스크에 남아 있었다. 방문이 뜸한
시간대엔 화면 문구("최대 1시간 뒤 지웁니다")보다 실제로 더 오래 남을 수 있었다는 뜻이다.

**09-02에 고쳤다.** `main.py`의 lifespan에서 asyncio 작업 하나를 띄워
`PRUNE_EVERY_SEC = 10분`마다 `_prune_uploads()`를 부른다. 새 패키지는 안 붙였다.
요청을 한 번도 안 보낸 상태로 확인하는 테스트를 `test_prune.py`로 남겼다
(`python -m pytest test_prune.py -q` → 1 passed). 자세한 건
[P15](../plan/문제점/P15-업로드정리주기.md). 배포 서버(Render)에 직접 파일을 올리고 1시간 기다려
실제로 없어지는지 보는 건 **Render 대시보드 접근이 있어야 하는 사람 몫**이라
오늘은 못 했다.
