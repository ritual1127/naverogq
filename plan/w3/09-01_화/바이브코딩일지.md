# 09-01 바이브 코딩 일지

> 오늘 AI에게 무엇을 시켰고, 무엇이 나왔고, 무엇을 내가 판단했는지 남긴다.
> 코드는 git에 남지만 **왜 그렇게 시켰는지는 여기 아니면 안 남는다.**

W3 첫날 계획은 세 줄이었다 — 워크샵 강의 읽기 · 핵심 행동 한 문장 · 만들 것/안 만들
것 나누기. 전부 문서 작업이라 생각보다 일찍 끝났다. 거기서 멈추지 않고 **09-02부터
09-07까지 걸려 있던 나머지 W3 산출물 셋(아키텍처 · AI 사용 기록 · 보안 점검)을
전부 하루에 당겨서 냈다.** 그 과정에서 계획에 없던 진짜 문제 두 개를 찾았다.

## 1부 — 새로 쓴 게 아니라 흩어진 걸 묶었다

`docs/mvp.md`를 만들라고 시켰을 때 처음 걱정한 건 "8주 남았는데 안 만들 것을
뭘로 채우나"였다. 그런데 실제로 읽어 보니 결정은 이미 다 있었다 — `roadmap.md`에
"공개문제 3회차 확보 전엔 코드 안 건드림", `policy.md`에 "회원가입 없음", 인터뷰
기록에 "표본 1명이라 검사 항목 안 늘림". **한 문서로 묶은 적이 없었을 뿐이다.**

그래서 지어내지 말고 각 항목에 출처 링크를 달게 했다. 표 아홉 줄 중 지어낸 건
"도면 자동 수정 안 함" 한 줄뿐이다 — 이건 문서 어디에도 없던 결정이라 오늘
처음 정한 것으로 표시했다.

인터뷰에서 나온 요청 중 **안 만들 것으로 분류한 항목**(재질 기입 · 요목표 ·
비교표 · A4 출력 잘림)을 표에 반드시 넣으라는 게 계획 문구였다. 이건 원래
`roadmap.md`의 "검사 자체가 없는 항목" 표에 이미 있던 걸 그대로 옮긴 것이다 —
새로 판단한 게 아니라 **이미 내린 판단을 W3 형식에 맞게 재배치**한 것에 가깝다.

## 2부 — 캐시가 두 종류라는 걸 그림에서 처음 구분했다

아키텍처 1장을 만들 때 README의 기존 mermaid에는 캐시가 한 상자였다. 그런데
`ai_review.py`를 다시 읽어 보니 `SHIPPED_CACHE`(저장소 안, 심사에서 그대로 보임)와
`CACHE_DIR`(`%LOCALAPPDATA%`, 로컬에만 남음)가 **다른 경로**였다.

```python
SHIPPED_CACHE = os.path.join(os.path.dirname(os.path.abspath(__file__)), "aicache")
CACHE_DIR = os.path.join(
    os.environ.get("LOCALAPPDATA") or os.path.expanduser("~"),
    "cad-checker", "aicache")
```

저장소의 `aicache/`를 직접 열어 보니 **비어 있었다.** 배포판에 미리 채워 둔
캐시 예시가 없다는 뜻이다. 이걸 그림에서 숨기지 않고 "지금은 비어 있다"고
그대로 적었다. 심사에서 폴더를 열어 볼 수도 있는데 문서와 실제가 다르면
그게 더 큰 문제다.

## 3부 — "왜 그 모델을 골랐나"는 코드에 답이 있었다

AI 사용 기록의 핵심은 "심사 피드백이 지적한 대로 각 모델을 왜 골랐는지"였다.
근거 없이 "성능이 좋아서" 같은 말을 못 쓰게 막아 뒀길래, `ai_review.py` 상단의
모델 상수부터 확인했다.

```python
GEMINI_MODEL = "gemini-3.6-flash"
CLOUDFLARE_MODEL = "@cf/meta/llama-4-scout-17b-16e-instruct"
GROQ_MODEL = "qwen/qwen3.6-27b"
MISTRAL_MODEL = "mistral-small-latest"
```

네 개의 순서(Gemini → Workers AI → Mistral → Groq)는 이미 `policy.md`에 있었지만
**왜 그 순서인지**는 어디에도 안 적혀 있었다. Cloudflare가 배포 인프라라 같은
계정으로 바로 열 수 있다는 것, Groq가 속도 우선의 마지막 보루라는 것 — 이건
새로 판단해서 써야 했다. 짐작이 아니라 실제로 각 서비스를 왜 그 자리에
넣었는지 되짚어서 근거를 달았다.

**프로덕트 AI와 개발 도구 AI를 섞지 말라**는 계획 문구도 그대로 지켰다.
`policy.md`에 이미 두 목록이 있었는데 한 문서에서는 나눠서 안 보여준 적이
없었다. 표 두 개로 쪼갰다.

## 4부 — "깨끗합니다"로 끝날 뻔한 걸 두 번 물렸다

보안 점검표가 오늘 제일 중요한 부분이었다. 처음 나온 결과는 "1·3번 클린,
2·4번도 문제없음"이었다. **여기서 멈추지 않고 근거를 다시 보여 달라고 시켰다.**

2번(`.env`가 `.gitignore`에 있는지)을 다시 확인하니 **없었다.**

```
grep -n "\.env" .gitignore   →  0건
```

지금 커밋된 `.env` 파일은 없지만, 누군가 로컬에서 만들어 쓰다가 실수로
`git add`하면 그대로 새는 구조였다. 발견한 자리에서 바로
`.env`·`.env.*`를 추가해 막았다. **점검이 "확인했다"에서 끝나지 않고
"고쳤다"로 이어진 첫 번째 자리다.**

4번(업로드가 실제로 1시간 뒤 지워지는지)에서 더 큰 걸 찾았다. `main.py`를
읽어 보니 정리 함수가 이렇게 불린다.

```python
def _run(job, path, name, enabled=None):
    _prune_uploads()
    try:
        facts, findings, summary = check.analyze(path, enabled=enabled)
```

**크론이 아니라 새 검사 요청이 들어올 때만 도는 구조였다.** 화면에는 "최대
1시간 뒤 지웁니다"라고 적어 뒀는데, 트래픽이 뜸한 시간대엔 그 다음 요청이
올 때까지 계속 남아 있을 수 있다. 로직 자체가 틀린 건 아니라서 로컬에서
확인만 하고 넘어갈 수도 있었다.

```
old 남음: False   ← 1시간 2분 지난 폴더, 지워짐
new 남음: True    ← 방금 만든 폴더, 안 지워짐
```

로직은 맞다. 그런데 **"1시간 뒤 지운다"는 화면 문구와 "다음 요청이 와야
지운다"는 실제 동작이 다르다는 것 자체가 문제**라고 판단해서 새로 고치지 않고
[P15](../../문제점/P15-업로드정리주기.md)로 남겼다. 스케줄러를 새로 붙일지
문구만 정확하게 바꿀지는 오늘 안 정했다 — 둘 다 일리 있고, 이건 담당자가
30분 안에 정할 문제지 지금 혼자 결정할 문제가 아니다.

Render 실서버에 직접 도면을 올리고 1시간 기다려 보는 확인은 **대시보드
접근이 없어서 못 했다.** 못 하는 걸 했다고 안 적고 안대열 몫으로 그대로
남겼다.

## 5부 — 안 시킨 것도 하나 봤다

09-07 계획에 있던 "Render 콜드스타트 확인"이 눈에 띄어서 미리 봤다.
`.github/workflows/keepalive.yml`의 cron이 이렇다.

```
*/5 0-14,18-23 * * *   (UTC)
```

UTC로 15~17시가 스케줄에 없다. KST로 바꾸면 **매일 00:00~03:00경에는
안 깨운다.** 실제로 헬스 엔드포인트를 두 번 찔러 확인했다.

```
1차: 12.82초, HTTP 200
2차(직후): 0.42초, HTTP 200
```

촬영이 그 새벽 구간과 안 겹치면 상관없지만, 겹치면 촬영 직전에 반드시
깨워야 한다. 09-07 계획 메모에 적어 뒀다 — 새로 확인할 게 아니라
그때 시간만 대조하면 되게 만들어 뒀다.

## 오늘 배운 것

- **문서형 산출물은 새로 쓰는 일보다 흩어진 결정을 찾아 묶는 일이었다.**
  안 만들 것 표 아홉 줄 중 지어낸 건 한 줄뿐이고, 나머지는 저장소 어딘가에
  이미 있었다.
- **"확인했더니 깨끗합니다"에서 한 번 더 밀어붙이니 진짜 문제가 나왔다.**
  `.env` 누락과 업로드 정리의 요청-트리거 구조는 둘 다 첫 확인에서는
  "문제없음"으로 넘어갈 뻔했다.
- **로직이 맞는 것과 문구가 정확한 것은 다르다.** `_prune_uploads()`는
  틀리지 않았다. 그런데 화면 문구가 그 로직의 한계를 가리고 있었다.
- **못 하는 건 했다고 안 하고 남긴다.** Render 대시보드가 필요한 확인
  둘(환경변수 실측·실서버 삭제 확인)은 억지로 흉내내지 않고 그대로
  담당자 몫으로 남겼다.
