# 08-31 바이브 코딩 일지

> 오늘 AI에게 무엇을 시켰고, 무엇이 나왔고, 무엇을 내가 판단했는지 남긴다.
> 코드는 git에 남지만 **왜 그렇게 시켰는지는 여기 아니면 안 남는다.**

W2 마지막 날이다. 계획은 세 줄 — 멘토 공유 · 실제 도면으로 정확도 재기 · W3 페이지 열기.
그중 하나는 사람 몫이고, 하나는 **도면이 없어서 시작조차 못 하는 것**이었다.

## 1부 — 제출 글을 네 번 다시 썼다

먼저 W2 산출물을 멘토에게 보낼 한 편의 글로 만들라고 시켰다. 처음에 나온 건
마크다운 표에 링크가 잔뜩 달린 문서였다. 저장소 안에서는 맞는 형식인데,
**붙여넣을 곳이 게시판이라는 걸 내가 안 말했다.** `docs/interviews.md` 로 가는
링크가 열 개 넘게 박혀 있었고, 받는 사람은 그걸 하나도 못 누른다.

두 번째는 링크를 빼게 했고, 세 번째는 표까지 빼고 문단 글로 바꿨다. 그런데
이번엔 너무 길었다. 인터뷰 다섯 건에 직접 인용을 세 개씩 그대로 넣으니
읽는 사람이 끝까지 못 간다. 네 번째에 4,000자 아래로 줄이라고 했고
**2,909자**가 됐다. 인용은 사람마다 가장 결정적인 한 줄만 남겼다.

여기서 내가 판단한 것 하나. 다른 팀 자동 피드백 두 건을 보니 감점 사유가
**설문으로 대체 · 개별 인터뷰 미제출 · 문제 정의 한 문장이 다른 글 안에 묻힘**
이었다. 그래서 형식을 강의 요구 그대로 맞췄다 — 인터뷰 5건을 **개별로**,
질문과 답변을 나눠서, 문제 정의는 **따로 떼서 한 문장만**.
줄이라고 해서 이 구조까지 줄이면 요구를 못 맞춘다.

인터뷰 기록에 비어 있던 칸(장소 · 길이 · 학년)도 오늘 채웠다.
**이건 내가 만난 사람에게 확인해서 준 값이고, AI가 채운 게 아니다.**
도면 수령 칸만 `미기록`으로 남겼다. 받은 게 없으니까.

## 2부 — "0장이라 못 합니다"에서 멈출 뻔했다

오늘의 진짜 항목은 실제 도면으로 정확도를 다시 재는 것이었다.
`실제도면/labels.json` 은 `{}` 그대로고, `bench.py` 는 이렇게 끝난다.

```
FAIL: 실제도면/labels.json 에 도면이 한 장도 없다. 0장으로는 정확도를 잴 수 없다.
```

이 줄이 뜬 건 나쁜 게 아니다. 08-26에 0장인데 100%가 찍히던 걸 막아 둔
([P09](../../문제점/P09-빈측정100.md)) 결과가 제대로 동작한 것이다.
그래서 AI는 "못 했음, 09-01로 넘김"으로 정리하고 커밋까지 했다. 기록으로는 정확하다.

**그걸 물렸다.** 인터뷰로 도면을 받는 길이 막혔으면 다른 길을 찾아보라고 시켰다.
컴퓨터 전체에서 `.dwg`·`.dxf` 를 훑게 했더니 16개가 나왔다. 그중
SMC 카탈로그 도면(cylinder · vacuum)은 부품도가 아니라 뺐고, 08-22에 무늬 도면으로
확인된 것도 뺐다. 남은 게 **`1본체.dxf` 와 `3축.dxf`** — 한국어 레이어(외형선 ·
은선 · 중심선), 주서, 부품번호 ①②, 거칠기 w/x/y, 단면 E-E 가 들어 있는 진짜 부품도다.

수험생에게 받은 도면은 아니다. 그래서 **표본으로 세지 않기로 했고**
`docs/accuracy.md` 의 정확도 표도 안 바꿨다. 두 장으로 퍼센트를 만들면
지금까지 합성 도면 100%를 문제라고 적어 온 게 우스워진다.

## 3부 — 우리가 만든 도면에서는 절대 안 나올 버그

두 장을 넣었더니 **두 장 모두에서 같은 지적이 났다.**

```
EX_NO_FIT  error  끼워맞춤 공차 기호가 없음
```

이게 사실인지 확인하려고 도면 원문을 직접 뒤지게 했다. 여기서 중요한 건
**CADLens 결과로 CADLens를 채점하지 않는 것**이다. `exam.py` 를 거치지 않고
DXF 안의 치수 문자를 그대로 뽑았더니 이렇게 나왔다.

```
1본체 : Ø<>H7  ×2
3축   : Ø<>js5 , <>h6
```

**있는데 못 본 거였다.** 원인은 규칙 한 줄이었다.

```python
_ISO_FIT = re.compile(r"\d\s*[A-Za-z]{1,2}\d{1,2}(?![\d.])")
```

숫자 뒤에 오는 기호만 찾는다. 그런데 실제 CAD 도면은 측정값을 `<>` 로 두고
기호를 뒤에 붙인다(`Ø<>H7`). 숫자가 문자열에 없다. 우리가 만든 합성 도면은
**우리가 숫자를 직접 써 넣어서**(`Ø47H7`) 이 규칙이 통했다.

이게 오늘 제일 크다. [발전 계획](../../../docs/roadmap.md) 1번에
"도면을 만든 사람과 검사 규칙을 만든 사람이 같아서 실제 도면에서도 맞는다고
말할 수 없다"고 두 주 전부터 적어 뒀는데, **그게 실제로 무슨 뜻인지 오늘 처음
숫자로 봤다.** 합성 100장에서 100%가 나오는 것과 실제 도면에서 맞는 것은 다른 일이다.

고친 건 한 곳이다. `exam.plain_dim_text()` 로 MTEXT 서식을 걷어내고 `<>` 를
숫자로 바꾼 뒤에 기존 규칙 셋에 태운다. 치수 문자를 읽는 입구가 한 군데뿐이라
거기서 고치면 `EX_NO_FIT` · `EX_TOL_FEW` 가 같이 낫는다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 1본체.dxf | 지적 5건 | 지적 3건 |
| 3축.dxf | 지적 4건 | 지적 2건 |

합성 100장은 그대로 100%, 시험 20개 통과.

## 4부 — 남은 둘을 안 고친 이유

지적 둘이 남았다. `EX_DIM_MISSING`(1본체 21곳)과 `DQ_NO_GEOMETRIC_TOL`
(두 장 다 **실격** 판정)이다. 둘 다 헛지적처럼 보인다.

특히 기하공차 쪽은 AI가 "AIGDT 글꼴이 쓰였으니 기하공차가 있는 것이고
규칙을 고쳐야 한다"고 했다. 그런데 원문을 더 보니 그 글꼴은 대부분
**치수 앞의 지름 기호(Ø)** 로 쓰이고 있었다. 그대로 고쳤으면 이번엔
지름 기호를 기하공차로 세는 반대쪽 오답이 됐다.

1본체에는 치수 71·85 옆에 글꼴 문자 두 개가 따로 떠 있는데,
이게 기하공차 기입틀인지 아닌지는 **도면을 눈으로 열어 봐야 안다.**
[P04](../../문제점/P04-표본도면.md) 에 그대로 적고 안 고쳤다.
추측을 원인으로 적으면 나중에 그게 사실인 줄 알게 된다.

## 오늘 배운 것

- **"없어서 못 했습니다"는 결론이 아니라 중간 보고다.** 도면을 받는 길이 하나
  막혔다고 오늘 할 일이 끝나는 게 아니었다. 두 장을 찾는 데 10분 걸렸다.
- **표본을 우리가 만들면 우리가 아는 것만 검사하게 된다.** 오늘 나온 버그는
  합성 도면을 1,000장으로 늘려도 안 나온다.
- **AI가 대는 원인 중 절반은 그럴듯한 추측이다.** 원문을 직접 뽑아 확인한 것만
  고쳤고, 확인이 안 된 것은 열어 뒀다.
