## 증상

W8 KPI 리포트를 쓰려고 2026-10-03 에 `/api/stats` 를 읽었다.

```
"retention":[{"cohort":"2026-09-28","size":2,"weeks":[]},
             {"cohort":"2026-09-21","size":3,"weeks":[{"since":"2026-09-28","back":5,"rate":1.667}]}]
```

09-21 주에 처음 온 사람이 3명인데, 그다음 주에 돌아온 사람이 5명이다. **분자가 분모보다 클 수
없다.** W6 제출본을 만들 때(09-28 18:31) 같은 칸은 `back 1 · rate 0.333` 이었다.

## 원인

코드로 확인한 것까지만 적는다.

`stats.RETENTION_SQL` 은 처음 온 사람(`new`)과 다시 온 사람(`ret:처음온주`)을 둘 다
`COUNT(DISTINCT visitor)` 로 센다. `visitor` 는 `소금 + 그 주 + IP` 를 해시한 값이다.
그런데 "처음 온 주"는 브라우저(`localStorage` 의 `cadcheck.first`)가 기억한다. **세는 단위는
IP 인데 묶는 단위는 브라우저다.** 둘이 어긋나면 두 방향으로 틀린다.

1. **같은 브라우저가 그 주에 IP 를 바꿔 오면 여러 명이 된다.** 집 · 학교 · 휴대폰 데이터로
   한 번씩 오면 `ret` 이 셋이다. 분자가 부푼다.
2. **같은 IP 에서 처음 온 브라우저 여러 개는 한 명이 된다.** 학교 실습실처럼 인터넷 주소를
   같이 쓰면 `new` 가 하나로 합쳐진다. 분모가 줄어든다.

이번 5명이 어느 쪽인지는 원자료(`hits`)를 봐야 알고, **아직 안 봤다.** 09-21 코호트 3명은
배포 직후(09-23 저녁 ~ 09-24)에 처음 온 브라우저라 팀 브라우저가 섞였을 수 있다는 것은
[`docs/metrics.md`](../../docs/metrics.md#리텐션-커브)에 이미 적어 두었다.

## 조치 (안 — 아직 안 넣음)

- 화면이 코호트 이벤트를 **브라우저마다 한 주에 한 번만** 보낸다. 마지막으로 보낸 주의
  월요일 날짜만 `cadcheck.*` 자리에 둔다. 남는 것은 여전히 날짜뿐이라 개인정보 약속은 그대로다.
- 서버는 `new` · `ret` 을 `COUNT(DISTINCT visitor)` 대신 `SUM(n)` 으로 센다. 한 브라우저가
  한 주에 한 번만 보내므로 단위가 IP 가 아니라 브라우저가 된다.
- 지난 기록은 되돌려 고칠 수 없다. 지금까지 `ret` 의 `n` 은 페이지를 열 때마다 올랐다.
  **고친 날 이후 처음 온 코호트부터** 보여 준다.

## 확인 (고친 뒤 할 것)

- 같은 브라우저가 IP 둘로 와도 `ret` 1, 같은 IP 의 브라우저 둘은 `new` 2 인지 보는 시험을
  `test_events.py` 에 넣는다.
- 배포 뒤 첫 코호트의 1주 뒤 칸에서 `rate` 가 1 을 넘지 않는지 본다.
