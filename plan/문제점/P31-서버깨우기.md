## 증상

10-08 에 10-19 까지 계획을 짜며 사이트 유지보수 쪽을 보다가 GitHub Actions 실행 기록을 셌다.
[`keepalive.yml`](../../.github/workflows/keepalive.yml) 은 5분마다(`*/5 0-14,18-23 * * *` — 한국 시간 0 ~ 3시를 뺀
21시간) 공개 서버의 `/api/health` 를 부르게 돼 있다. 계획대로면 하루 252번이다.

| 날짜 (UTC) | 09-27 | 09-28 | 09-29 | 09-30 | 10-01 | 10-02 | 10-03 | 10-04 | 10-05 | 10-06 | 10-07 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 실제 실행 | 6 | 4 | 4 | 5 | 5 | 4 | 6 | 6 | 3 | 5 | 4 |

09-27 ~ 10-08 의 실행 54번 사이 간격은 2.4 ~ 9.3시간, 가운데 값 5.3시간이다(`gh run list --workflow keepalive.yml`). 최근 300번(08-25 ~ 10-08) 중 실패는 4번이고
모두 10-02 ~ 10-03 — 메모리 초과로 서버가 재시작하던 때다([P27](P27-공개서버502.md)).

문서에는 "GitHub Actions 가 5분마다 깨운다"고 적혀 있다 — [`docs/화면_기능명세.md`](../../docs/화면_기능명세.md),
[W8 KPI 리포트](../w8/W8_KPI리포트.md) ⑤ 지속 가능성. 실제와 다르다.

## 원인

GitHub 의 예약 실행(`schedule`)은 적은 시각에 돈다는 보장이 없다. GitHub 문서는 부하가 클 때 예약 실행이 늦어지고,
부하가 아주 크면 빠질 수도 있다고 적고 있다. 5분 간격을 적어도 실제로는 몇 시간에 한 번 돌았다.

## 영향 — 아직 모름

Render 무료 서버는 15분 동안 요청이 없으면 잠든다(Render 문서). 잠들면 처음 들어온 사람이 서버가 깨어나기를 기다린다.
깨우기가 몇 시간에 한 번뿐이니 **서버를 깨워 두는 것은 우리 장치가 아니라 그때그때 들어오는 요청**이다.

- **실제로 얼마나 자주 잠드는지는 모른다.** 10-08 22:04 에 `/api/health` 를 부른 뒤 이쪽에서 17분 동안 아무 요청도
  안 보내고 22:22 에 다시 불렀더니 0.35초에 왔다 — 깨어 있었다. 그 사이 다른 요청(로봇 · 다른 사람)이 깨웠을 수 있다.
- 잠든 서버가 깨어나는 데 몇 초 걸리는지는 **아직 못 쟀다.** 10-09 02:57 (깨우기 쉬는 시간이 끝나고 Worker 가 처음 깨우기 전)에
  재 봤더니 0.85초(바로 다음 0.64초) — 이번에도 깨어 있었다. 우리 쪽 마지막 요청은 01:22 GitHub 예약 실행이고 그 뒤 95분 동안
  우리 쪽 요청은 없었다. 왜 깨어 있었는지는 모른다 — 다른 요청(로봇 · 다른 사람)이 있었을 수 있다.
- 기다리다 그냥 나간 사람이 있었는지, 몇 명인지는 셀 방법이 없다.

## 조치

2026-10-09 00:44 — 이미 쓰는 Cloudflare 계정에 Worker [`keepalive/`](../../keepalive/)(`cadlens-keepalive`)를 올렸다.

- 계획은 Cron Trigger 였는데 **안 걸렸다** — "This account has reached the Workers Free limit of 5 cron triggers per account"
  (code 10072). 이 계정의 다른 Worker 들이 무료 칸 5개를 다 쓰고 있다. 다른 프로젝트의 칸은 건드리지 않았다.
- 대신 **Durable Object 알람**으로 돌린다. 알람이 울리면 `/api/health` 를 부르고(한국 시간 0 ~ 3시는 건너뜀) 5분 뒤 알람을
  다시 건다. 깨우다 실패해도 다음 알람은 건다(`finally`).
- 알람이 끊기는 경우를 위해 GitHub 예약 실행(`keepalive.yml`)이 돌 때마다 Worker 주소를 불러, 알람이 없으면 다시 건다.
  예약 실행이 실패하면 오던 메일 감시도 그대로 남는다.

## 확인

Worker 주소 https://cadlens-keepalive.smilepea.workers.dev/ 를 열면 다음 알람(`next`)과 마지막으로 깨운 기록(`last`)이 보인다.

- ✅ 00:44 에 알람을 건 뒤 다음 알람 시각이 정확히 300초 뒤로 옮겨진 것을 확인했다(`next` 1791474316657 → 1791474616657).
- ✅ 01:22 에 GitHub 예약 실행이 돌며 '알람 다시 걸기' 단계가 실제로 Worker 를 불렀다 — 응답 `{"next":1791476717045,"last":null}`
  (다음 알람 01:25:17). 00:45 부터 알람이 끊기지 않고 이어졌고, 쉬는 시간이라 깨운 기록은 아직 없었다.
  이 실행 시각은 예약 시각표에 없는 시각이다(UTC 15 ~ 17시는 뺐다) — 원인 절의 "적은 시각에 돈다는 보장이 없다"와 같은 일.
- ✅ **03:05 부터 실제로 깨운다** — 03:06 과 03:11 에 Worker 주소를 열어 `last` 를 읽었다. 간격 300초.

  | 읽은 시각 | 깨운 시각 (`last.at`, 한국 시간) | 응답 | 걸린 시간 |
  |---|---|---|---|
  | 03:06:00 | 03:05:18 | 200 | 105ms |
  | 03:11:01 | 03:10:18 | 200 | 126ms |

- ✅ **하루 동안 끊기지 않았다(10-10).** 다음 알람 시각(`next`)이 10-09 00:45:16 에 건 뒤로 300초 간격 그대로다 —
  10-10 01:56:16 · 02:41:16 · 02:46:16 · 02:51:16 으로, 315번 동안 한 번에 0.2초씩 밀려 1분 늦어졌을 뿐 자리가 바뀐 적이 없다.
  끊겼다가 GitHub 예약 실행이 다시 걸었다면 아무 초에나 걸렸을 것이다. 쉬는 시간(0 ~ 3시) 앞 마지막 깨우기는 10-09 23:56:14(200 · 89ms),
  뒤 첫 깨우기는 10-10 03:01:16(200 · 139ms). 03:01:42 에 `/api/health` 0.83초.
- ⬜ Render 대시보드 Logs 에서 서버가 새로 켜진 기록이 하루 몇 번인지 — 고치기 전 하루와 고친 뒤 하루를 견준다.
  고치기 전에 여러 번 켜졌다면 그때마다 누군가 기다렸을 수 있다.
- 🔺 잠든 서버의 첫 응답 시간 — 10-09 02:57:01 에 `/api/health` 0.85초. 깨어 있어서 못 쟀다(영향 절).
