# 문제점

일하다 만난 문제를 **그때그때 적어 두는 폴더**입니다. 고쳤든 못 고쳤든 남깁니다.

왜 남기나 — 문제를 고치고 나면 그런 문제가 있었다는 사실 자체를 잊습니다.
8주 뒤 발표에서 "무엇을 어떻게 알아냈는가"를 말할 수 있는 팀과 "잘 됩니다"만
말하는 팀은 여기서 갈립니다. 심사 피드백도 **안 되는 걸 공개하는 것**을 우리 강점으로
꼽았습니다.

## 원칙 — 없는 문제를 지어내지 않는다

**실제로 겪은 것만 적습니다.** 그날 아무 문제도 없었으면 아무것도 적지 않습니다.
기록을 채우려고 "개선하면 좋을 점" 같은 것을 문제로 올리지 않습니다.
지어낸 문제가 한 건이라도 섞이면 나머지 기록도 같이 못 믿게 됩니다.
빈 주가 있는 게 정상이고, 그게 이 폴더가 진짜라는 증거입니다.

문제인 것 — 실제로 틀린 결과가 나왔다, 하려던 게 안 됐다, 시간이 계획보다 훨씬 더 들었다,
연락이나 자료가 없어서 막혔다.
문제가 아닌 것 — 아직 안 만든 기능, 다음에 하기로 한 일, 잘 됐는데 더 잘하고 싶은 것.
그런 건 [발전 계획](../../docs/roadmap.md)이나 그날 계획에 적습니다.

## 적는 법

1. **새 문제**를 만나면 파일 하나를 만듭니다. 이름은 `P08-짧은이름.md`처럼 번호를 이어 붙입니다.
2. 머리표를 채웁니다 — 상태 · 처음 본 날 · 무엇에 영향을 주나 · 맡은 사람.
3. 본문은 **증상 → 원인 → 조치 → 확인** 순서로 씁니다. 원인을 모르면 모른다고 적습니다.
   추측을 원인 칸에 적으면 나중에 그게 사실인 줄 알게 됩니다.
4. **이미 있는 문제가 진전되면 그 파일 맨 아래 `## 기록`에 날짜와 한 줄을 더합니다.**
   새 파일을 만들지 않습니다.
5. 고쳤으면 상태를 `해결`로 바꾸고 **확인 절에 무엇으로 확인했는지 숫자나 명령으로** 남깁니다.
   "고쳤습니다"만 적힌 건 확인이 아닙니다.
6. 위 현황 표도 같이 고칩니다.

## 규칙

- **못 고친 문제를 지우지 않습니다.** 열린 채로 두는 게 정상입니다.
- 처음 짐작이 틀렸어도 지우지 않습니다. 무엇을 잘못 짚었는지가 기록입니다.
  ([P02](P02-AI점수편차.md)가 그런 경우입니다. 백지 때문이라고 봤는데 아니었습니다.)
- 사람 문제(연락이 안 온다 같은 것)도 적습니다. 코드 문제만 문제가 아닙니다.
- **`/today-plan` 을 돌릴 때마다 그날 만난 문제를 여기에 적습니다.**
  **그날 아무 문제도 없었으면 아무것도 안 적습니다.**
